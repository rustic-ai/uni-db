# Teeth ledger — 2026-08-13

Evidence that this suite catches the bugs that motivated building it.

Phase 5's premise: *"an oracle that cannot re-catch the bugs that motivated it is
not yet correct, and this is the only phase that proves it can."* A test that has
only ever been observed passing is not evidence. This ledger records, per bug,
what happened when the defect was deliberately put back.

Reproduce with:

```bash
scripts/testing/teeth_validate.sh            # all six
scripts/testing/teeth_validate.sh issue_097  # one
```

Each patch is applied inside a throwaway `git worktree`, so an interrupted run
cannot leave a reverted fix in your tree.

---

## How to read this

Every row carries two independent results:

| column | meaning |
|---|---|
| **control** | A pre-existing regression test that must **fail** under the patch. If it passes, the run aborts — the usual cause is a cached binary, and every later result would be measuring the fixed code. |
| **oracle** | Whether a **generated** case caught it. `—` means no generated case can reach the bug, with the blocking capability named. |

`—` in the oracle column is a finding, not an omission. It says exactly which
fixture or lever capability is missing.

## 1. Lance `"col"` range fusion — the generated catch

**What it was.** `LanceFilterGenerator` fused `p >= L AND p <= U` into the string
`"p" >= L AND "p" <= U`. Lance's filter dialect parses a double-quoted name as a
**string literal**, so the clause was really `'p' >= L AND 'p' <= U` — a constant
with no reference to the data. For that operator pair it is false for every row,
so the scan returned nothing.

Reaching it needs all three of (`bugs/hash_index_range_quoting.rs:15-23`):
1. a **Hash** scalar index on the column,
2. an `=` or `IN` on it — what populates `PushdownStrategy::hash_index_columns`,
3. a two-sided **inclusive** range on the same column.

Drop any one and the predicate never reaches the generator, "which is why the
plain `WHERE p >= 2 AND p <= 4` form always looked correct."

**Revert kind: reconstruction, not revert.** The fix *deleted* the fusion, so
there is nothing to invert. The patch instead quotes the column in
`FilterExpr::Compare`'s `to_sql`, scoped to `GtEq`/`LtEq` only. Quoting
unconditionally would be over-broad — it would break every pushed predicate and
prove merely that *some* pushdown bug is catchable, rather than this one.

Note the patch deliberately violates an invariant the file documents at
`types.rs:156-163`: *"Column names are emitted bare, and must stay that way …
adding quotes to 'harden' it would silently turn every predicate into a
constant."* That comment is the fix's own account of the defect.

**Measured.**

| run | result |
|---|---|
| `bugs::hash_index_range_quoting::eq_plus_two_sided_range…` | **FAIL** — control |
| `bugs::hash_index_range_quoting::in_list_plus_two_sided_range…` | **FAIL** |
| `bugs::hash_index_range_quoting::range_still_constrains…` | PASS — **non-discriminating**, see below |
| `dqp::flush_lever::flush_smoke` (before Phase 5) | PASS — **the oracle was blind** |
| `dqp::flush_lever::flush_pushdown_smoke` (after) | **FAIL** — `bag mismatch: left_total=28, right_total=0` |

`left=28, right=0` is the defect's signature: L0 evaluates the predicate in
process and returns 28 rows; Lance receives a string constant and returns none.
The failure prints replay coordinates
(`DQP_SEED=59109665097449476 DQP_BATCH=0 DQP_CASE=0`).

**A non-discriminating test lives beside the bug.**
`range_still_constrains_when_it_excludes_the_equality` asserts `got.is_empty()`
— and the bug *also* yields empty. It passes identically with and without the
defect. It is a sound test of the opposite direction and a non-witness for this
bug, which is why `teeth_validate.sh` names a specific control test per bug
rather than running the whole file.

**What made the catch possible** (none of it generator *shapes*):
- `SchemaMode::TypedIndexed` — the fixture had no index at all before.
- `arb_same_column_conj` — `arb_pred` topped out at two comparisons with
  independently-drawn targets, so three conditions on one column had probability
  zero.
- The delta-domain fix below.

**A latent defect found on the way.** The first pushdown run failed at **63.6%
activation**, under the 80% floor. Cause: `FlushLever`'s delta wrote five of the
fixture's seven `AGE_DOMAIN` values, so a generated `age = 22` predicate matched
fixture rows but no *unflushed* row — and the lever's entire premise is that
side A reads unflushed rows. Unfiltered `Plain` cases never exposed it: two
thirds carry no base `WHERE` and scan the delta wholesale. Only a case kind that
always filters could reveal it. Fixed by drawing the delta from `AGE_DOMAIN`
itself; activation **63.6% → 86.6%**.

That failure was the activation floor doing its job. Lowering it to 60% would
have turned everything green while making the oracle permanently weaker, with
nothing recording the trade.

## 2. #135 — traversal props NULL after flush

**Why the oracle cannot reach it, and no generator change would help.**

`build_edge_adjacency_and_target_props` (`traverse.rs:2628`) has exactly **one**
caller: `traverse.rs:2903`, inside `impl Stream for GraphTraverseMainStream`.
That stream is planned only when
`!unknown_types.is_empty() && edge_type_ids.is_empty()` (`planner.rs:5405`) — i.e.
only when **every** requested relationship type is absent from the schema.

Both harness fixtures declare `WORKS_AT`, so every generated query plans through
typed `Traverse` and cannot reach the fix site. Confirming detail: the #135
regression test declares label `MCTSNode` but never declares its `PARENT` edge
type — that omission is exactly why it reproduces.

**Blocking capability:** a schemaless-edge fixture mode. Costly, because
`bulk_insert_edges` rejects an undeclared type (`transaction.rs:857`), so edges
would have to go through Cypher `CREATE` — roughly two orders of magnitude
slower, forcing a smaller tier. Deferred; not needed once the `"col"` fusion met
exit criterion 3.

**Guarded against regression** by `dqp::seed::tests::typed_fixture_plans_a_typed_traverse`,
which asserts the fixture's plan does *not* contain `TraverseMainByType`. If the
fixture ever goes schemaless, that test fails and says so.

**The revert here is the naive one, and it is DQP-invisible.** Returning
`HashMap::new()` nulls target properties on **both** sides of a differential
comparison, and an oracle cannot see a defect that corrupts both sides
identically. It is faithful enough for the existing regression test, which
compares a traversal against a *node scan*. A DQP-visible revert would have to be
tier-selective (restoring L0-only hydration rather than dropping everything).

That distinction generalizes beyond this bug: **a differential oracle is blind to
any defect that damages both of its sides equally.** It is the same blindness
`dqp/mod.rs` records for TLP and NoREC.

## 3. #097, #099, #103, #110 — fork-dependent

All four have true one-line reverts and existing regression suites, and none is
reachable from a generated case today. Each needs a distinct lever capability:

| bug | blocking capability |
|---|---|
| #097 | A fork of a parent holding committed-but-unflushed L0. `drive_prepared_with` flushes the fixture unconditionally before `prepare`, so the precondition cannot be constructed. Needs a per-lever `FLUSH_BEFORE_PREPARE` opt-out plus a delta written before the fork. |
| #099 | Schemaless data — a target-label predicate compiles to a `hasLabel` filter only on the schemaless path. Same blocker as #135. |
| #103 | A **nested** fork (fork of a fork) over an indexed fixture; `use_scalar_index(false)` only matters at chain depth > 1. Note it would surface as an *execution error*, not a bag diff. |
| #110 | `Direction::Incoming` in the generator (`rel_element` hardcodes `Outgoing`), plus a post-fork relationship write to populate the direction overlay. |

#097 is the closest to reachable, and its blocker — the unconditional pre-run
flush — is worth fixing regardless of teeth, since it makes the fork lever
structurally blind to an entire bug class.

#110 may not want a lever at all. A **direction-inversion structural law** —
`(a)-[:R]->(b)` and `(b)<-[:R]-(a)` must return equal bags, since pattern
direction is a traversal choice and not a semantic one — is precisely the
invariant #110 violated, costs far less than a lever variant, and would run as a
permanent guard.

## Maintenance

`teeth::every_revert_patch_still_applies` runs in the PR lane (`git apply
--check`, milliseconds, no build). When a fix site moves, it fails and forces the
patch to be regenerated — which is the moment to re-validate the tooth.

It checks only that a patch *applies*, never that the defect is still catchable.
That claim needs the full harness; conflating the two would let a rotted tooth
report itself healthy.

The full harness is **not** wired into CI: it builds the workspace once per bug,
and patches rot against a moving tree, so a rotted patch would fail nightly with
no bug behind it.
