# ANN recall@10 vs QPS — SIFT-1M

**Date:** 2026-08-25
**Bench:** `crates/uni/benches/ann_pareto.rs`
**Tree:** `83587ee4c`
**Track:** E2a / B3
**Fixtures:** `sift1m-base`, `sift1m-query`, `sift1m-groundtruth` (see `docs/fixtures.md`)

Regenerate with:

```bash
python3 scripts/fixtures/fetch.py --only sift1m-base --only sift1m-query \
    --only sift1m-groundtruth
cargo bench -p uni-db --bench ann_pareto
```

## What makes this measurable

Recall here is **externally defined**. SIFT ships the true top-100 neighbours per
query under L2, so the numbers below are not scored against an oracle we wrote.
The exact (`flat`) cell is the proof that the comparison is sound: it recalls
**1.0000** against SIFT's own answers at the full million, which confirms the
metric, the ingest ordering and the truth source all line up. Every other row is
only meaningful because that one is exact.

`dense_retrieval.rs` remains the other experiment — synthetic corpus, one query
vector, cosine, our own brute-force oracle, recall and latency reported
separately. This bench is the ann-benchmarks protocol: real corpus, many
queries, external truth, recall plotted against throughput.

## Results

Intel Core Ultra 9 185H, 22 cores, 62 GiB, Linux 7.1.8, rustc 1.98.0. Release.
n = 1,000,000 · 128-d · L2 · K = 10 · 50 queries per cell (3 for the exact cell).
HNSW `m=16, ef_construction=100, partitions=1024`; IVF_PQ `partitions=1024,
sub_vectors=16`. Full sweep 3m01s including three ingests and index builds.

| index | knob | recall@10 | QPS |
|---|---|---:|---:|
| flat (exact) | — | **1.0000** | 6.3 |
| hnsw | ef_search=10 | 0.8620 | 20.4 |
| hnsw | ef_search=25 | 0.9600 | 32.6 |
| hnsw | ef_search=50 | 0.9800 | 32.6 |
| hnsw | ef_search=100 | 0.9800 | 32.1 |
| hnsw | ef_search=400 | 0.9800 | 27.6 |
| ivf_pq | nprobes=1 | 0.2580 | 59.4 |
| ivf_pq | nprobes=16 | 0.5360 | 60.7 |
| ivf_pq | nprobes=64 | 0.5620 | 50.8 |
| ivf_pq | nprobes=128 | 0.5620 | 45.4 |
| ivf_pq | nprobes=16, refine=5 | 0.8220 | 58.9 |
| ivf_pq | nprobes=16, refine=20 | 0.8680 | 56.5 |
| ivf_pq | nprobes=64, refine=5 | 0.9260 | 52.3 |
| **ivf_pq** | **nprobes=64, refine=20** | **0.9920** | **49.1** |

## What the curve says

**1. IVF_PQ with `refine_factor` is the best point on the curve, and it is not
close.** 0.992 recall at 49 QPS — better recall *and* 50% more throughput than
the best HNSW cell (0.980 at 32.6), and 8x the exact scan. Anyone choosing a
dense index on this workload should choose IVF_PQ with refine.

**2. `refine_factor` is nearly free and enormous.** At `nprobes=64` it moves
recall 0.562 → 0.992 for a 3% throughput cost (50.8 → 49.1 QPS). PQ stores lossy
codes, so probing ranks candidates on approximate distances; refine over-fetches
and re-scores against the original vectors. Without it, more probing cannot help
— recall is flat from `nprobes=64` to `128` — because the ceiling is precision,
not search.

**3. The default is a trap.** `uni.vector.query` with no `refine_factor` on an
IVF_PQ index returns **0.56 recall** and reports nothing unusual. That is a
silently poor answer from a correctly-built index, and it is the shape of defect
this suite exists to find. An IVF_PQ index almost certainly wants a refine
default above 1, or a loud note at index-creation time; the knob is documented
but nothing signals that omitting it halves recall.

**4. HNSW saturates at `ef_search=50`.** Recall stops improving there (0.980)
and QPS falls monotonically after. `ef_search` 25–50 is the useful band; the
`1.5xk` default of 15 lands near 0.862 and is too low for a recall-sensitive
workload.

**5. Both families clear the proposal's §8.2 95% recall target** — but only
IVF_PQ with refine clears it while also beating the exact scan by 8x.

**6. Flush dominates ingest.** ~27s of the ~40s build, independent of index
family, which is the path the defect below lives in.

## The defect this benchmark found

The first attempt at 1M produced a table where **every cell of both families
returned recall 0.9990 at 8.1 QPS** — identical across `ef_search` 10→400 and
`nprobes` 1→128. The non-vacuity gate rejected it. Chasing that produced a
product defect with a minimal reproduction.

### Chain

1. **`flush_to_l1` silently breaks the barrier it documents.**
   `crates/uni-store/src/runtime/writer.rs` — its rustdoc states it is a
   *"SYNCHRONIZATION BARRIER — callers rely on it as 'all writes are now durably
   in Lance'"*. It drains in-flight async flushes with
   `let _ = coord.drain(self.config.drop_fork_drain_timeout).await` — the result
   is **discarded**, and the bound defaults to **10 s**. Above roughly 600k rows
   the drain does not finish, and `flush()` returns `Ok` having not flushed.
2. **The index build then declines, quietly.** `create_vector_index_inner` finds
   `!table_exists`, logs at `debug!` level, and returns
   `BuildOutcome::NotAttempted`.
3. **`NotAttempted` is reported as `Online`.** The enum's own doc comment says
   so: *"Currently mapped to `Online`, which is a known gap and not an
   endorsement."*
4. **Queries fall back to an exact scan of the unflushed L0** — hence recall
   ≈ 1.0 with the ANN knobs inert.

Each link returns success. Nothing above `debug!` is emitted anywhere in the
chain, and `rebuild()` returns `Ok(())`.

### Reproduction

Bisected on corpus size, then confirmed by changing one variable:

| n | drain bound | flush | index build | `ef_search` 10 → 400 |
|---:|---|---:|---:|---|
| 200,000 | 10s (default) | 5.2s | 2.2s | 0.675 → 0.985 |
| 400,000 | 10s (default) | 10.0s | 5.1s | 0.560 → 1.000 |
| 600,000 | 10s (default) | **10.0s** | **0.0s** | — |
| 700,000 | 10s (default) | **10.0s** | **0.0s** | 1.000 → 1.000 (inert) |
| 700,000 | **900s** | 18.0s | 9.7s | **0.720 → 0.960** |
| 1,000,000 | **900s** | 25.7s | 13.9s | **0.620 → 0.978** |

The flush time pinning to exactly 10.0s is the tell: a cap, not a measurement.
Raising only `drop_fork_drain_timeout` restores the index build and the knob
response at unchanged corpus size, which isolates the cause to that bound and
its discarded result.

### Why it matters beyond benchmarks

`flush_to_l1` is described in its own comments as what fork setup and shutdown
paths rely on for durability, and the discarded drain meant those callers got the
same silent partial guarantee above the same volume.

**Fixed 2026-08-26.** The drain result is propagated instead of discarded, and
the bound moved from `drop_fork_drain_timeout` (10s, documented for `drop_fork`)
to a named `flush_drain_timeout` defaulting to 120s. A drain that does not finish
is now an error naming what was not established:

```
flush_to_l1 barrier not established: pending flushes did not drain before
deadline (waited 1ms); writes are not yet durable in Lance
```

Verified in both directions: at the shipped default a 700k-row corpus now
flushes in 18.3s and builds its index in 5.2s with `ef_search` live again
(0.880 → 0.960), where it previously capped at 10.0s with a 0.0s index build and
inert knobs; and with the bound forced to 1ms the error above fires rather than
returning success. `ann_pareto.rs` no longer needs its configuration workaround.

The `ann_pareto` non-vacuity gate is the regression test: it is what rejected the
silent-success state in the first place, and a return of this defect reproduces
the same signature (every cell of both families at identical recall and QPS).

A second, smaller finding: `drop_fork_drain_timeout` is documented as *"Maximum
time `drop_fork` will wait for pending async flushes on that fork"*, but governs
the general flush barrier. A field doing load-bearing work far from its
documented purpose is how a 10s default ends up bounding a bulk load.

### A lead that dissolved

An early reading of the same broken state showed the exact cell at **0.011 QPS**
— ~91 s per query — which looked like an independent performance defect in the
exact vector path. It was not. With the corpus genuinely flushed the same cell
runs at **2.3 QPS**, a 200× difference. The slowness was the unflushed L0 being
scanned, i.e. the same root cause. It is recorded here because it was nearly
published as a separate finding.


## Root cause of the HNSW anomaly — found and fixed

The table above was measured **before** this section's fix. It showed HNSW
Pareto-dominated by brute force, with QPS inelastic to `ef_search`. That is now
explained, and it was not the index.

### What the measurements ruled out

Each hypothesis was tested by changing one variable at fixed corpus size, and
each was **falsified**:

| hypothesis | test | result |
|---|---|---|
| Degenerate partition count | `partitions: None` vs `Some(1024)` at n=400k | recall at low `ef` improved 0.595 → 0.890, **QPS unchanged** (2.0 → 2.3) |
| Per-query index *payload* load | `HnswFlat` / `HnswSq` / `HnswPq` at n=400k — payload size varies ~10x | **QPS identical** (2.3 / 2.4 / 2.3) |
| Per-query *graph* load | `m = 4 / 16 / 48` at n=400k — graph size varies 12x | **QPS identical** (2.5 / 2.4 / 2.4) |

Every ANN parameter moved recall and none moved time. `EXPLAIN` was no help:
uni's logical plan is an identical `ProcedureCall` for both families.

### What the profile showed

`perf record` over a run where HNSW queries are ~96% of samples:

| cost | share |
|---|---:|
| **HNSW graph search** (`IvfSubIndex`, `HnswLevelView::neighbors`, `beam_search`) | **~6.3%** |
| Lance page decode / copy (`DecodeMiniBlockTask`, `_copy_to_iter`, `memmove`, `unravel_offsets`) | ~15.4% |
| malloc / free | ~6.5% |
| locking, futex, scheduler | ~5.5% |
| f32 L2 distance | 4.9% |

The graph traversal we had blamed is a twentieth of the time. The cost is
data materialization, spread thin — the signature of re-reading and re-decoding
the same bytes on every query.

### The cause

`LanceDirectory::builder` built every dataset open as
`DatasetBuilder::from_uri(uri)` and **never supplied a `Session`**. In Lance 7,
`DatasetBuilder::with_session` is documented as *"Re-use an existing session.
The session holds caches for index and metadata."* With `session: None` each
open gets a fresh one, so **Lance's index and metadata caches were cold on every
single query**. `LanceDirectory::open` deliberately never caches the `Dataset`
handle — for a good reason, since a cached handle pins a manifest version and
would miss rows from a later flush — and that correct decision silently threw
away the block caches too.

The fix is to hold one `Arc<Session>` on `LanceDirectory` and pass it to every
builder. Freshness is preserved: each open still loads the current manifest, and
only content-addressed index and metadata blocks are reused.

### Measured effect

Same corpus, same parameters, only the shared session added (n=200k,
partitions=1024):

| cell | before | after | speedup |
|---|---:|---:|---:|
| hnsw `ef_search=10` | 3.9 | **41.4** | 11x |
| hnsw `ef_search=100` | 3.6 | **84.1** | **23x** |
| hnsw `ef_search=400` | 4.0 | 67.8 | 17x |
| ivf_pq `nprobes=16` | 114 | 150.6 | 1.3x |
| flat (exact) | 11.5 | 13.2 | 1.2x |

Recall is unchanged (0.98 at `ef_search=100`). Two qualitative changes matter
more than the multiplier:

- **QPS is elastic to `ef_search` again** (41 → 84), instead of pinned. The knob
  now costs what it should.
- **HNSW is 6x faster than brute force** rather than 3x slower. Finding 1 above
  — "HNSW is Pareto-dominated by brute force" — was an artifact of this defect,
  not a property of the index.

The gain scales with index size, which is why IVF_PQ (16 bytes/vector) barely
moved while HNSW gained an order of magnitude.

**The headline table at the top of this document was re-measured at 1M with the
fix** and is the corrected result. The pre-fix 1M numbers, for the record:

| index | knob | recall@10 | QPS (pre-fix) | QPS (fixed) |
|---|---|---:|---:|---:|
| flat | exact | 1.0000 | 2.3 | **5.5** |
| hnsw | ef_search=25 | ~0.95 | 0.8 | **31.9** |
| hnsw | ef_search=400 | ~0.97 | 0.8 | 26.9 |
| ivf_pq | nprobes=4 | ~0.46 | 52.8 | 65.6 |

HNSW gained **~40x** at 1M. The whole sweep fell from 8m36s to 2m53s.

## Non-vacuity

Three ways this bench could print a table describing nothing, and the guard for
each. All three are enforced, and the second one is what caught the defect above.

| failure mode | guard |
|---|---|
| Metric, ingest order or truth source misaligned | the exact cell must recall ≥ 0.99 against ground truth, else exit 1 |
| The sweep knob never reaches the engine | each swept family's recall must have nonzero spread, else exit 1 |
| Corpus small enough for Lance to brute-force, so the index never runs | perfect recall across a whole family below n=1M is refused, naming `fork_index_recall_bench.rs` as the precedent |
| Ground truth silently wrong for a subset | SIFT's answers describe the full million; any smaller n recomputes truth by brute force and labels every line `truth=recomputed (subset)` |
| A run reports coverage it does not have | the closing witness names only families that actually produced ≥2 points; with none it says "anchor only, not a curve" |

The last row was itself a bug in the first version of this bench: it printed
"both swept families moved recall" on a run where `ANN_INDEXES` had excluded
both.

## Limits, stated

- **One machine, one run.** QPS is not comparable across hardware and gates
  nothing. Only `hot_paths_iai.rs` gates perf, on instruction counts.
- **50 queries per cell**, 3 for the exact cell. SIFT ships 10,000. Recall at
  n=50 has a standard error of roughly ±0.02, which is fine for separating 0.62
  from 0.978 and too coarse for ranking two configurations a point apart.
- **Single-threaded QPS.** Queries are issued sequentially, so these are
  latency reciprocals, not a saturated-throughput measurement.
- **The workaround is in the measurement.** Every number above was taken with
  `drop_fork_drain_timeout` raised to 900s. At the shipped default this corpus
  does not index at all.
- **HNSW parameters are one point**, `m=16, ef_construction=100`. A different
  build could move the curve; the finding that its QPS is inelastic to
  `ef_search` would not obviously change.
- **`refine_factor` was swept only at `nprobes` 16 and 64**, values 5 and 20.
  The optimum is not bracketed; a finer sweep may find a cheaper point than 20.
